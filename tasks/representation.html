2.1 Formatos de representación de datos

2.1.1 CSV (Comma-Separated Values)

El formato CSV es ampliamente utilizado para representar datos tabulares. Cada línea del archivo representa un registro (un caso, un individuo, un objeto, etc.), y los valores dentro de cada registro están separados por comas. De este modo, todos los valores situados en la misma columna comparten el mismo tipo de dato, que debe ser conocido de antemano. El esquema del archivo CSV define la estructura de los datos, es decir, cuántas columnas tiene el archivo y cuál es el nombre y tipo de cada una de ellas.

Este formato es fácil de leer y escribir, y es compatible con muchas herramientas de análisis de datos. Sin embargo, no soporta tipos de datos complejos ni estructuras jerárquicas, lo que puede limitar su uso en ciertos escenarios. CSV se utiliza habitualmente en aplicaciones como bases de datos y hojas de cálculo, que ofrecen soporte nativo para este formato por su facilidad para efectuar operaciones de importación y exportación. Además, ha sido tradicionalmente utilizado en el intercambio de datos entre diferentes sistemas y plataformas, debido a su simplicidad y compatibilidad con múltiples lenguajes de programación. El hecho de que sea un formato de texto plano permite que se pueda inspeccionar su contenido (human-readable) usando un editor de texto, posibilitando la depuración y limpieza de los datos. Sin embargo, esta estrategia es inviable para archivos de gran tamaño, ya que la lectura y escritura de archivos de texto plano puede ser lenta y consumir muchos recursos. En estos casos, se recomienda utilizar formatos binarios optimizados, que veremos más adelante en este capítulo, para el almacenamiento y procesamiento de datos.

Conviene tener en cuenta algunos aspectos sobre el trabajo con archivos CSV:

  • Separadores: Aunque el formato CSV utiliza comas como separadores por defecto, algunos archivos pueden utilizar otros caracteres, como punto y coma (;) o tabulaciones (\t). En este último caso, el formato se suele denominar TSV (Tab-Separated Values). Resulta esencial conocer el separador utilizado en el archivo para poder leerlo correctamente.

  • Encabezados: Los archivos CSV pueden incluir una fila de encabezado que contiene los nombres de las columnas. Esta fila suele ser la primera del archivo, pero no siempre es así. Es importante comprobar si el archivo contiene un encabezado y, en tal caso, asegurarnos de que se interprete correctamente esta información.

  • Valores faltantes: Los archivos CSV pueden contener valores faltantes o nulos, que se representan mediante celdas vacías (espacios en blanco entre dos separadores). Debemos prever cómo vamos a manejar estos valores al leer y procesar los datos, ya que pueden afectar a los resultados del análisis.

  • Codificación de caracteres: Los archivos CSV pueden utilizar diferentes codificaciones de caracteres, como UTF-8, ISO-8859-1 o Windows-1252. Es fundamental definir la codificación del archivo para poder leerlo correctamente y evitar problemas de interpretación de caracteres especiales.

  • Comillas: Los valores de texto en los archivos CSV pueden estar entre comillas (simples o dobles) para permitir la inclusión de caracteres especiales, como comas o saltos de línea, dentro de los valores. Cuando cargamos el archivo, debemos comprobar que las comillas se procesen correctamente para evitar errores en la interpretación de los datos.

  • Dialectos: Existen diferentes dialectos de CSV, que definen una combinación de aspectos de formato como el separador, el uso de comillas o la presencia de encabezados. Es importante saber el dialecto en el que se expresa el archivo para leerlo correctamente y evitar problemas de interpretación de los datos.

2.1.2 JSON (JavaScript Object Notation)

El formato JSON (https://www.json.org/json-es.html) es un estándar abierto que utiliza una estructura de objetos y arrays para representar datos. Es un formato de texto plano (human-readable) que sea eficiente tanto para humanos (a la hora de editarlo) como para máquinas (a la hora de procesarlo). Su principal domino de uso reside en aplicaciones web y APIs, siendo compatible con muchos lenguajes de programación.

Está constituido por dos estructuras principales: objetos y arrays.

  • Los objetos se representan mediante pares clave-valor. Pueden ser de distinta índole, incluyendo registros, estructuras, diccionarios, tablas hash, listas de claves (sets) o arrays asociativos. Cada clave es única dentro del objeto y se utiliza para acceder a su valor correspondiente. Los valores pueden ser de diferentes tipos, como cadenas de texto, números, booleanos, nulos, objetos anidados o arrays.

  • Los arrays son listas ordenadas de valores, que en la mayoría de lenguajes corresponden a arrays, vectores, listas o secuencias.

A pesar de que se trata de un formato muy común de intercambio de datos en aplicaciones y sistemas web, APIs y otros servicios de publicación de datos, JSON puede ser menos compacto a la hora de representar la misma información que otros formatos binarios optimizados, como Parquet o Avro. Además, no soporta tipos de datos complejos ni estructuras jerárquicas, lo que puede limitar su uso en ciertos escenarios.

2.1.3 XML (eXtensible Markup Language)

El formato XML es un lenguaje de marcado que representa datos estructurados y jerárquicos. Es ampliamente utilizado en aplicaciones empresariales y sistemas de intercambio de datos debido a su flexibilidad y capacidad para definir esquemas personalizados. Fue especialmente popular en los años 90 y principios de los 2000. Sin embargo, XML puede resulta ser el menos compacto y eficiente de los formatos de representación de datos en texto plano, puesto que requiere más espacio de almacenamiento y tiene un procesamiento más complejo en comparación con otros formatos como JSON o CSV.

En R, el paquete xml2 (https://cran.r-project.org/web/packages/xml2/index.html) proporciona funciones para leer y escribir archivos XML de manera eficiente. La función read_xml() permite importar datos desde un archivo XML a un objeto de tipo xml_document, mientras que la función write_xml() permite exportar un objeto xml_document a un archivo XML.

2.1.4 YAML (YAML Ain’t Markup Language)

YAML es un lenguaje de serialización o aplanado de datos en texto plano, para representarlos de manera amigable para los humanos. Su empleo se ha popularizado sobre todo en archivos de configuración y escenarios donde la claridad y la simplicidad son importantes. YAML puede representar estructuras jerárquicas y es compatible con muchos lenguajes de programación, aunque puede ser más propenso a errores de sintaxis debido a su especial sensibilidad a la indentación.

2.1.5 Parquet

Parquet es un formato de almacenamiento de datos en columnas, optimizado para el procesamiento de grandes volúmenes de información. Esta orientación columnar permite un acceso más eficiente a los datos, ya que solo se leen las columnas necesarias para una consulta específica, lo que reduce el tiempo de lectura y mejora el rendimiento en comparación con los formatos basados en filas.

Lo encontramos con frecuencia en entornos de big data y sistemas distribuidos de procesamiento de datos debido a su eficiencia en términos de almacenamiento y rendimiento. Parquet permite comprimir y codificar los datos, reduciendo el espacio de almacenamiento y mejorando la velocidad de lectura/escritura. Además, es compatible con muchos sistemas actuales de procesamiento de datos, como Apache Spark. 2.1.6 Avro

Avro es un sistema de serialización de datos que permite representarlos de manera compacta y eficiente. También se utiliza en entornos de big data y sistemas de mensajería, gracias a que puede manejar esquemas dinámicos y es compatible con múltiples lenguajes de programación. Avro puede comprimir los datos y es adecuado para situaciones que requieren un rendimiento alto en operaciones de lectura y escritura.

Su principal diferencia respecto a Parquet es que Avro está orientado a filas, mientras que Parquet está orientado a columnas. Esto significa que Avro es más eficiente para operaciones de escritura y lectura de registros completos o intercambio de datos, mientras que Parquet es más eficiente para consultas analíticas que requieren acceder a un subconjunto de columnas (por ejemplo, cuando seleccionamos un subconjunto de features). El hecho de que deba combinar diferentes tipos de datos en un mismo registro hace que Avro sea menos eficiente en términos de compresión y rendimiento que Parquet, especialmente cuando se trata de transferencias de grandes grandes volúmenes.

2.1.6.1 Soporte para Avro en R

El paquete sparklyr ofrece soporte para Avro desde su versión 1.3 (https://posit.co/blog/sparklyr-1-3#avro), permitiendo leer y escribir archivos Avro en R. La función spark_read_avro() permite importar datos desde un archivo Avro a un data frame de Spark, mientras que la función spark_write_avro() permite exportar un data frame de Spark a un archivo Avro. Puedes consultar el post en el blog de Posit del enlace anterior para ver un ejemplo de cómo utilizar estas funciones.

2.1.7 ¿Cuándo utilizar Parquet o Avro?

En general, podemos considerar las siguientes recomendaciones cuando tengamos que elegir entre uno de los dos formatos en nuestro proyecto:

  • Parquet: Es más adecuado para análisis de datos y consultas analíticas, en las que seleccionamos un subconjunto de columnas. Algunos ejemplos de plataformas de procesamiento ideales para esta estrategia son Apache Spark y Databricks, Snowflake, Google BigQuery o Athena, entre otros. Su orientación columnar permite un acceso más eficiente a los datos y una mejor compresión, lo que lo hace ideal para entornos de big data y sistemas distribuidos de procesamiento de datos.

  • Avro: Es más adecuado para captura de eventos uno por uno a gran velocidad, por ejemplo, cuando estamos leyendo de sistemas de ingesta de datos de altas prestaciones como Apache Kafka. También es adecuado para el intercambio de datos entre sistemas (como diálogo entre microservicios). Otro escenario donde Avro puede ser más adecuado es cuando se requiere un esquema dinámico, ya que permite manejar cambios en la estructura de los datos sin necesidad de modificar el código de la aplicación.

2.1.8 Apache Arrow

Apache Arrow puede almacenar datos en memoria optimizando su procesamiento por columnas. Sus principales ventajas son un alto rendimiento y escalabilidad, especialmente trabajando con datos en memoria. También soporta la interoperabilidad entre diferentes lenguajes de programación y sistemas, lo que facilita el intercambio de datos. Además, es compatible con técnicas de compresión y codificación de datos, incrementando la velocidad de lectura y escritura.

2.1.8.1 Relación con Arrow IPC (Feather)

Feather (https://arrow.apache.org/docs/1.0/python/feather.html) es la representación en disco del formato Apache Arrow para datos en memoria. Mientras que Arrow define cómo se organizan los datos columnares en la memoria RAM, Feather (concretamente, desde su versión 2) es el formato de archivo binario utilizado para almacenar esa misma estructura en disco (almacenamiento persistente) sin necesidad de transformar los datos, que se denomina técnicamente Arrow IPC (Inter-Process Communication). Poco después de lanzarse Apache Arrow en 2016, Wes McKinney (autor de la biblioteca pandas de Python) y Hadley Wickham (autor del ecosistema Tidyverse de R) crearon Feather como una prueba de concepto para demonstrar cómo se podían intercambiar data frames entre Python y R sin necesidad de usar formatos intermedios, como CSV.

La función read_arrow() permite importar datos desde un archivo Feather (en disco) a un data frame (en memoria), mientras que la función write_arrow() permite exportar un data frame a un archivo Feather. 2.2 Almacenamiento de datos

2.2.1 Bases de datos relacionales

Las bases de datos relacionales (RDBMS) son sistemas de gestión de bases de datos que utilizan un modelo basado en tablas para almacenar y organizar datos. Cada tabla contiene filas (registros) y columnas (campos), y las relaciones entre las tablas se establecen mediante claves primarias y foráneas. Estos sistemas aparecen con mucha frecuencia en aplicaciones empresariales y sistemas de gestión de información en producción, ya que pueden manejar grandes volúmenes de datos estructurados y a su compatibilidad con el lenguaje SQL (Structured Query Language).

2.2.2 Bases de datos NoSQL

Las bases de datos NoSQL son sistemas de gestión de bases de datos que no utilizan un modelo relacional tradicional. En su lugar, emplean diferentes modelos de datos para organizar la información, como documentos, pares clave-valor, grafos o columnas. Son muy útiles para procesar datos no estructurados o semi-estructurados, lo que las hace ideales para aplicaciones web, análisis de big data o sistemas distribuidos. Algunos ejemplos populares de bases de datos NoSQL incluyen MongoDB (documentos), Redis (clave-valor), Neo4j (grafos) y Cassandra (columnas).

2.2.2.1 Redis

Redis es una base de datos NoSQL de tipo clave-valor que almacena datos en memoria, ofreciendo un acceso rápido y eficiente. Destaca en entornos que requieren alta velocidad y baja latencia, como sistemas de caché, colas de mensajes y análisis de datos en tiempo real. Redis implementa características avanzadas como persistencia de datos, replicación, alta disponibilidad y soporte para estructuras de datos complejas, convirtiéndolo en la opción ideal para gran variedad de casos de uso.

2.2.3 Sistemas de almacenamiento en la nube

Los sistemas de almacenamiento en la nube permiten almacenar y acceder a datos a través de Internet, utilizando servicios proporcionados por proveedores de nube como Amazon Web Services (AWS), Microsoft Azure y Google Cloud Platform (GCP). Estos sistemas ofrecen escalabilidad, alta disponibilidad y redundancia, lo que permite a las organizaciones manejar grandes conjuntos de datos sin preocuparse por la infraestructura subyacente. Además, los sistemas de almacenamiento en la nube suelen ofrecer características avanzadas como cifrado, control de acceso y gestión de versiones, lo que mejora la seguridad y la integridad de los datos almacenados.

2.2.4 Bases de datos analíticas

Las bases de datos analíticas están diseñadas específicamente para tratar grandes volúmenes de datos y generar informes (interfaces interactivas o documentales). Estas bases de datos optimizan el almacenamiento y las operaciones de consulta mediante técnicas como la indexación, la agregación y la partición de datos. Se han vuelto soluciones muy demandadas en entornos de inteligencia de negocio (BI) y análisis de big data, y son compatibles con herramientas de visualización y análisis de datos como Tableau o Power BI. Algunos ejemplos incluyen Amazon Redshift, Google BigQuery y Snowflake.

2.2.4.1 Snowflake

Snowflake es una plataforma de almacenamiento y análisis de datos en la nube que ofrece un enfoque basado en la separación del almacenamiento y el procesamiento, permitiendo a los usuarios escalar recursos según sus necesidades sin afectar el rendimiento. Además, Snowflake es compatible con múltiples formatos de datos, incluyendo CSV, JSON, Parquet y Avro, y ofrece características avanzadas como seguridad, control de acceso y gestión de versiones. Destaca por su facilidad de uso (muy intuitiva), su rendimiento y su capacidad para integrarse con otras herramientas y servicios en la nube.

2.2.4.2 DuckDB

DuckDB es una base de datos analítica embebida que permite realizar consultas SQL directamente en archivos de datos locales, como CSV, Parquet y JSON. Es especialmente aconsejable para entornos de desarrollo y pruebas, evitándonos configurar un servidor de base de datos completo. DuckDB ofrece un rendimiento eficiente y escalable, y es compatible con múltiples lenguajes de programación, incluyendo Python, R y C++. Es ideal para escenarios donde se requiere un análisis rápido y flexible de los datos sin necesidad de una infraestructura compleja.
